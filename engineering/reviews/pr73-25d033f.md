## Findings

### S1 (Minor). Fail paths that return before the output step leave the previous run's verify.png AND its PASS verify.json in the out dir
- **Where:**
  - scripts/verify.ts:34-36: usage error and unknown flag, exit 2.
  - verify.ts:49,52: build failure and missing html, exit 3.
  - Any uncaught throw between :63 and :91 (sim or goldens), exit 1 via node.
  - All of these return before the stale-PNG removal at :91 and before verify.json is written (:127).
- **Repro:** `mkdir o && cp <a PASS verify.json> o/ && echo stale > o/verify.png`, then add a tsc error to src/main.ts and run `npm run verify -- --hours 1 --out o`. Result: **exit 3**, and `o/` still holds the old **PASS** verify.json and the stale PNG. The same happens with `--hours 0` (exit 2) and with a mutant that throws in `runVerify` (exit 1).
- **Impact:** low. The exit code is loud, CI always starts from a fresh `verify-out/ci`, and the default out dir is keyed by build id. But someone who reuses `--out` and attaches the folder after a failed run would attach a stale PASS.
- **Fix:** once `--out` is known (right after parseArgs), remove `verify.json`/`verify.png` there. Alternatively, for any non-zero exit, write a minimal FAIL verify.json (`{schemaVersion, result:"FAIL", exit, reason}`), and wrap `main()` in a try/finally that does the same on a crash.

### N-a (Nit). No test pins the explicit `flagsDifferFromBuild` term; mutant M14 survives
- **Where:** verify.ts:85 / tests/verify.test.ts:203-215. The only differing-flag test uses `m4.enabled=0`, where the shipped-balance round-trip fails anyway.
- **Repro:** remove `&& !flagsDifferFromBuild`. The suite stays 29/29, but `verify --hours 1 --flags m4.enabled=2` now gives exit 0 PASS with a screenshot.
- **Suggestion:** add a CLI case with a differing value that still round-trips under the shipped balance (`m4.enabled=2`), expecting exit 4.

### N-b (Nit). Duplicate keys and repeated `--flags` are silently last-wins
- **Where:** scripts/verify/cli.ts:17 (`o.flags = parseFlags(v())` replaces earlier `--flags`) and cli.ts:32 (a later duplicate key overwrites).
- **Repro:** `--flags m4.enabled=0 --flags m4.enabled=1` and `--flags m4.enabled=0,m4.enabled=1` both give **exit 0 PASS** with effective flags `{m4.enabled:1}`.
- **Impact:** verify.json honestly records the effective flags, so this is never a false PASS for what actually ran. But a typo'd experiment silently runs the shipped config. Consider making a duplicate key or a repeated `--flags` a usage error (exit 2).
