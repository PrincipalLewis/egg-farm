## (c) Concurrency

- **Group:** `ci-${{ github.workflow }}-${{ github.head_ref || github.ref }}` with `cancel-in-progress: true` (ci.yml:14-16).
  - PR → `ci-ci-<head branch>`.
  - Push → `ci-ci-refs/heads/main`.
  - PR and push groups can never collide. A push to main and a PR whose head is named `main` (only possible from a fork) give `ci-ci-main` vs `ci-ci-refs/heads/main`, which differ.
- **m1, main pushes:**
  - Two merges in quick succession cancel the first main run. That SHA ends with a *cancelled* `gate` and no FF/WK result.
  - The PR body accepts this. But release tags and `release-asset.yml` key off specific main SHAs, and "only the newest main SHA is checked" means a tagged SHA may never have had a green run.
  - Suggest `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`. That keeps the PR savings, and main runs queue instead (the concurrency queue holds one pending run).
- **m2, branch-name key:**
  - `head_ref` is the bare branch name, so a fork PR from `someone:ci/diet` shares a group with our `ci/diet` PR and the two cancel each other.
  - Two PRs from the same head branch (for example into `main` and into an `rc/*` base) also cancel each other.
  - Suggest `${{ github.event.pull_request.number || github.ref }}`.
- **Draft runs cancel too:** if a ready PR is mid-run and the author converts it to draft and pushes, the new (all-skipped) run joins the group and cancels the real run. This is acceptable and consistent with the draft policy. Noted for awareness only.
