**M1 — major — `scripts/d2-guard.mjs:58-64`, `scripts/d2-kill-browser.mjs:57,63`: Playwright's own force-kill during `ctx.close()` is NOT detected, so F5(b) does not hold as claimed.**
- **Trace:** a persistent context's `doClose` returns "close-browser" (`node_modules/playwright-core/lib/coreBundle.js:40165-40168`). That calls `browserProcess.close`, which is `closeOrKill(DEFAULT_PLAYWRIGHT_TIMEOUT)` (`coreBundle.js:41264`). The timeout is 3e4 ms (`coreBundle.js:4733`).
- **What Playwright does:** if graceful close takes longer than 30 s, `closeOrKill` calls `kill()` (`coreBundle.js:41255`). That reaches `process.kill(-spawnedProcess.pid,'SIGKILL')` at `coreBundle.js:10115`. `ctx.close()` then resolves normally.
- **Why d2 misses it:** `closeCtx` (`d2-guard.mjs:58-64`) uses a 90 s watchdog, which is longer than 30 s. `close()` resolves as `'closed'`, so there is no timeout halt. `expectExit(launch)` (`d2-guard.mjs:59`) already announced the exit, so the unannounced-`close` watcher (`d2-guard.mjs:52`) stays silent. Result: no halt, no stop list, `playwrightKillPossible` stays unset, and the row can print PASS.
- **Test gap:** `tests/d2-guard.test.ts:80-87` uses `fakeCtx(() => new Promise(() => {}))`, a close that never resolves. Real Playwright resolves after its force-kill. The "close() never finishes → HALT" test therefore gives false assurance.
- **Scope:** the group signalled is `-spawnedProcess.pid`, which is d2's own unexited child, so nothing foreign is hit. The defect is that HoO's "detected-and-halted" condition is not met.
- **Repro:** run d2 with a browser whose graceful close stalls (for example, SIGSTOP its group from outside) for more than 30 s, on the normal end-of-rep `closeCtx` (`d2-kill-browser.mjs:63`).
- **Fix:** make the watchdog shorter than 30 s, or treat `close()` taking 30 s or more as "force-kill may have fired" and halt.

## Answers

### 1. Can anything signal a process the run didn't start?

For the moved kills, `recorded-pid.mjs`, `serve-own.mjs`, `d2-kill-browser.mjs` and `d2-guard.mjs`, I found no path to a foreign process.
- **Single signalling site:** `process.kill` at `recorded-pid.mjs:53`. It is reached only via `recordProblem` (`:35-47`), which enforces all of these:
  - the record is well-formed (`malformed`, `:28-33`);
  - `rec.parent === process.pid` (`:38`);
  - the boot id matches (`:39`);
  - the process exists and is not a zombie (`:41-42`);
  - the start time matches (`:43`);
  - the live `ppid === process.pid` (`:44`);
  - for a group signal, `pgrp === pid` (`:45`).
- **Forged records:** a forged record can at worst name another live child of the same node process. That includes a pid-file forgery (`d2-kill-browser.mjs:35` → `recordPid`, which requires a live non-zombie child). The worst case is d2's own vite leader.
- **TOCTOU:** the check and the kill run in one synchronous turn. An unreaped child holds its PID, because libuv reaps on the event loop. A group's PGID cannot be reused while any member, including a zombie leader, exists. So the window is bounded to our own group.
- **Group kills:** `detached` makes Node call `setsid`, so the browser or vite group is its own session. Foreign processes cannot join that group. Descendants that `setsid` away are not hit. They are reported only if they were in the snapshot.
- **`stopChild` and `stopGroup`:** `stopChild` refuses once Node has seen the exit. `stopGroup` does the same and signals nothing when the leader exited first; it reports only.
- **Leader reaped and PID reused:**
  - `survivors` (`recorded-pid.mjs:102-106`) never probes `-pid` when the PID shows a different start time. The kernel allows that only when no group with that id exists.
  - When the PID is absent, `groupProbe` sends signal 0 to `-pid` (`:93`). That delivers nothing. The worst case is a false 'members' report if the PID were reused as a group leader.
- **/proc reads:** they are `/proc/<one recorded pid>/stat` and `/proc/<pid>/task/*/children`. `groupMembers` (`:80-88`) is a bounded (512) BFS over the descendants of our own recorded leader. It is not a /proc enumeration and not name matching, and it never signals. In effect it is a descendant-tree walk, which HoO may want to rule on explicitly. A PID reused between `readStat(k)` and `childrenOf(k)` could in theory list a foreign process as a "member" in a report. It would never be signalled.
- **Pattern kills:** none.
- **Claude and other agents:** a process is reachable only if it is a live child of the node process that spawned it. Claude and other agents' processes are not, so they cannot be hit by these paths.
- **Outside the guarded API:** the only signals not routed through `killRecorded` are Playwright's own (m3, M1).

### 4. Rating of `tests/rule21-source.test.ts`

I rate it as a decent regression guard for the exact historical forms, and not a rule-21 control. Minor (m2).
- **Strengths:**
  - It scans `scripts/**` recursively plus `tests/*.ts` helpers.
  - Exactly 6 marked guarded sites in `recorded-pid.mjs` are allowed.
  - 49 fixtures are each caught.
  - There are look-alike negative controls.
- **Bypasses (by regex trace; I could not run node):**
  - `const k='ki'+'ll'; process[k](…)` is not caught. The `''` normalisation only removes empty strings.
  - A template-built `execSync(\`${'k'}ill …\`)` is not caught, because no rule sees a literal `kill`.
  - `process.kill?.(…)`, `process.kill.call(…)`, `const k = process.kill`, `Reflect.apply(process.kill, …)` and `import { kill } from 'node:process'` are not caught. `js-kill-call` needs `.kill(`.
  - A `process.kill` / `(pid)` split across two lines, or `process.` / `kill(pid)`, is not caught. A split with `.kill(` at the start of the next line is caught.
- **Scope gaps:**
  - `*.test.ts` files (for example `tests/serve-own.test.ts:106` and `tests/verify.test.ts:426`, both `ChildProcess.kill` on their own children) and anything under `tests/` subdirectories.
  - Extensions outside `.mjs|.cjs|.js|.ts|.sh|.bash|.py` (`.mts`, `.tsx`, `.yml`, `package.json` scripts).
  - Option-driven kills such as `spawnSync(..., { timeout })` (`scripts/verify.ts:128`), which kills its own child.
  - Anything outside `scripts/` and `tests/`.
- **Mitigation:** the real control is the single guarded site plus the runtime `process.kill` spy, not the regexes.
