## Findings

### 1. minor: `canPersist` is not the same predicate as `save()`, so the flag can be shown but not persisted
`src/game.ts:129` vs `src/game.ts:240-245`.
- Evidence: `save()` persists `this.hidden.state` while a hidden period is open (`base = this.hidden ? this.hidden.state : this.state`). The explainer sets the flag on `this.state` only. `canPersist` does not check `this.hidden`. It also ignores `storageFailed` and quota failures, which `save()` swallows (`game.ts:251`).
- Scenario: the commit lands while the Game is in a hidden period but `document.visibilityState` is still `'visible'` (platform freeze or pagehide paths set `hidden` without a visibility change), or the write throws `QuotaExceededError`. The card shows and `g.state.seenTracksExplainer` is true in memory, but storage never gets it. The next load re-shows the card, since the on-load rule still matches.
- Impact: repeat explainer for an edge-case player. The "only when the flag can be persisted" guarantee is weaker than the commit message says.
- Fix: add `&& !this.isHidden` (and optionally `&& !this.storageFailed`) to `canPersist`. Better still, derive `canPersist` and `save()`'s early returns from one helper.

### 2. minor: the retry loop never ends
`src/ui/tracks-explainer.ts:16`.
- Evidence: when `canPersist === false` or the tab is hidden, it calls `setTimeout(() => showTracksExplainer(g, doc), 1000)` with no cap and no exit.
- Scenario: `readOnly` from a newer save, a tab that is `inactive` after losing the lease (both permanent for the session), or `resetting`. A 1 Hz timer then runs for the life of the tab, and it holds `g` and `doc`. After `deactivate()` the user may never reload.
- Impact: small constant waste. It is not a correctness bug, but it is unbounded.
- Fix: stop retrying when `g.readOnly`, `g.inactive` or `g.resetting` is set (permanent states), or after a fixed number of tries. The on-load rule already covers a reload.

### 3. minor: the in-app reduced-motion setting is not honoured
`src/ui/styles.css:516-517` vs `src/ui/app.ts:55-57`.
- Evidence: the app has its own reduced-motion toggle (`rm()` sets `.reduced-motion` on `<html>` and `.rm` on the root). Neighbouring components handle both (`.reduced-motion .ios-tip`, `.reduced-motion .recovery-card`, `.rm .qpop`). The new card handles only `@media (prefers-reduced-motion:reduce)`.
- Scenario: a player turns reduced motion on in Settings while the OS setting is off. The card still plays the 0.9→1 scale pop, against art-ux v1.3 "Reduced motion on: no scale; a plain 150 ms opacity fade". The OS-setting case works.
- Fix: add `.reduced-motion .tracks-exp,.rm .tracks-exp{animation:expfade .15s linear}`.

### 4. minor: deviations from art-ux/m4-tracks-explainer.md v1.3, with no stated decision to drop them
`src/ui/tracks-explainer.ts`, `src/ui/styles.css:512`.
- Anchor and arrow: the spec says anchor to the tracks block when it is on screen (arrow, above or below), and top-centre only otherwise. The card is always fixed at `top:72px`, with no arrow and no anchoring. This is acceptable only if a HoP or Art & UX note allows the fallback everywhere. I found none in the diff.
- Fade-out: the spec says a 150 ms fade-out, in both the normal and reduced-motion variants. `close()` removes the element immediately.
- Persist "and again on dismiss": only persisted at show. Harmless, because the flag is already true.
- Impact: visual and behavioural drift from a locked UX spec. Not harmful, but the PR does not say it is a deliberate simplification.
- Fix: either implement them, or record the deviation in the commit or spec.

### 5. minor: tests are partly tautological, and key negative paths are missing
`tests/m4-exp1-explainer.test.ts`.
- Copy: it imports `EXP_TITLE` and `EXP_BODY` and compares to them (lines 41-42). The locked copy "Upgrades got an upgrade!" / "Hens and Egg value are now separate. Top them up!" is never pinned as a literal, so changed copy still passes.
- Timeout: `vi.advanceTimersByTime(EXP_MS)` uses the exported constant. `EXP_MS = 1` or `1e9` still passes, and the 8000 ms value in the spec is not asserted.
- On-load negative paths: the "fresh farm" test has no backup record at all. Nothing covers `tracksV7:1` with an orphan or foreign backup (id different from `v6BackupId`), or a fresh farm created while an orphan `v6_backup` exists. An implementation that checks only for the presence of a backup record would pass every test.
- Saves m1: the fake-game tests exercise `showTracksExplainer`, and the "real Game" test checks only the getter. No test mounts a real `readOnly` or `inactive` Game and asserts that no card appears and the flag is not set.
- "No scrim": the test only checks `nextElementSibling === null`. It does not assert that no `.scrim` exists, or that nothing else in the document intercepts pointer events.
- Copy and 8 s are also not pinned by any visual or Playwright check that I could see.
- Fix: assert literal copy and `8000`. Add a stale-backup-id case and a fresh-farm-with-orphan-backup case. Add one test with a real readOnly Game.

### 6. minor: the Saves m1 gate is not type-enforced
`src/ui/tracks-explainer.ts:9`, `:16`.
- Evidence: `type G = Pick<Game,'state'|'balance'|'save'> & { canPersist?: boolean }` and the check `g.canPersist === false`. The property is optional and the check treats `undefined` as "can persist".
- Scenario: someone renames or removes `Game.canPersist`. `tsc` still passes (the optional property is simply absent), the gate silently turns off, and the only failing test would be the one that reads `g.canPersist` on the real Game. No test runs the real `showTracksExplainer(game)` against a blocked game (see finding 5).
- Fix: type it as `Pick<Game, ... | 'canPersist'>` (required) and test with a real `Game`.

Keep the desktop-only parts (`min-width`, `.tab-pill` padding) and drop the duplicates in a later cleanup.

### 8. nit: card is positioned on the viewport, not the farm column, and ignores safe-area
`src/ui/styles.css:512`.
- At 360 and 390 the card is 296px wide (`min(296px, 100vw-32px)`), left edge at 32 and 47px, `top:72px` (HUD 56 + 16). That fits by arithmetic. I did not render it.
- At 1280 landscape the grid is `1fr 400px`, so the card centres at x=640 while the farm column centre is 440. It stays inside the farm column (x 492–788 < 880), so nothing is hidden, but it is off-centre against the farm.
- `top:72px` uses a hard-coded value where `.ios-tip` uses `calc(var(--hud-h) + var(--s-2) + env(safe-area-inset-top))`. The HUD itself ignores safe-area in this file, so this is consistent, but it is worth a look on notched phones.
- `z-index:27` puts the card above the welcome-back modal (20) and the onboarding hints (25-26). That is intended ("whatever screen"), and a tap on the modal dismisses and passes through.
- Fix: optional. Use `var(--hud-h)` instead of the literal 72.
