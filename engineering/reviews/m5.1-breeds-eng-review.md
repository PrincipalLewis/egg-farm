## 1. Incubator 60 s countdown across offline and reload (Q-HoE-1, BR-R8/R18/R20, §6)

**What RC1 actually has:**
- There's no saved sim clock. `GameState` (`src/sim/state.ts:6-29`) holds only relative timers (`nextCustomerInS`, `waitedS`, worker `cdS`, `manageCdS`). The only absolute time is the file-level `savedAt` (`src/save/save.ts:7`, written by `serialize`, `save.ts:144-146`).
- Offline time comes from timestamps only. On load: `grantOffline(now() - f.savedAt)` (`src/game.ts:94`), but only if `savedAt` passed `validSavedAt` (`game.ts:58`, `save.ts:190`: finite, > 0, ≥ 2020-01-01, and **not in the future**). An invalid or tampered `savedAt` gives 0 offline and is re-stamped (`game.ts:94,99`).
- When the tab is hidden for ≥ 60 s, the provisional hidden sim is **dropped** (`this.state = h.state`, `game.ts:376`) and the whole gap goes through the same `grantOffline` (`game.ts:378`), with the same `validSavedAt` check (`game.ts:360`). A hide shorter than 60 s keeps up to 60 s of online sim (`game.ts:363-374`).
- On a visible but throttled frame with a gap ≥ 60 s, the game simulates 60 s and freezes for the rest. There's no grant on this path (`game.ts:398-401`).
- The clamp is in `applyOffline`: `awayS = clamp(awayMs/1000, 0, offlineCapSeconds = 7200)` (`src/sim/offline.ts:23`). A gap under `offlineMinSeconds` (60) gives 0 (`offline.ts:8,16`). The tick is fixed at `tickHz` 10, so dt = 100 ms (`balance.json:3`, `tick.ts:94-98`).
- Autosave runs every 5 s plus on hide, pagehide and beforeunload (`balance.json:5`, `src/save/autosave.ts`).

**Evaluating the spec's assumption:** the spec stores a relative `remainingMs` and doesn't invent an absolute sim clock. That's correct for RC1, and it's the deterministic option. `incubatorEndsAtSimS` would need a new persisted sim clock that nothing else uses. A wall-clock `endsAt` would be open to clock tampering and would break the "sim time" semantics while the sim is hidden or frozen.

**Recommended rule (concrete):**
1. Persist `breeds.incubator.remainingMs` as an **integer**. Each `step` subtracts `dtMs = 1000/tickHz` (100). Add a balance check that `1000 % tickHz === 0`. The reveal fires on the first tick where `remainingMs ≤ 0`, i.e. 600 ticks.
2. **Offline:** decrement inside `applyOffline`, in the one place that serves both load and long hide. Use `remainingMs -= awayS × 1000` with the **same clamped `awayS`** (`offline.ts:23`), and only when `awayMs/1000 ≥ offlineMinSeconds`. Apply it even when the grant gives 0 eggs. Don't decrement by the spec's "full uncapped span". The result is the same today (any valid grant ≥ 60 s ≥ `remainingMs`, so the hatch always completes), but using the clamped value keeps one clamp and tamper rule if `bc_hatch_time_s` ever goes above 2 h.
3. **Tamper:** an invalid or future `savedAt` gives no grant and no decrement (inherited from `game.ts:94/360`). Moving the clock forward can't gain more than "the hatch completes", which any 60 s absence already gives.
4. **Reveal on load:** `Game` listeners aren't attached yet inside the constructor (`game.ts:94` runs before the UI subscribes). Queue the reveal the same way as `this.offline` (`game.ts:28,103`), with a `pendingReveal` field the UI reads after the welcome-back modal, not as a notify event. Put reveal and auto-slot in **one pure function** that both `step` and `applyOffline` call. The hidden provisional sim's state and events are discarded on a ≥ 60 s hide (`game.ts:376`), so a reveal must never log telemetry outside the SimEvent sink.
5. **Reload with a gap under 60 s:** no grant, so the incubator loses that gap, like every other sim timer. Up to 5 s (one autosave interval) can be lost. Keep the spec's wording.
6. **Pause the incubator offline?** No. Run it as above (answer to Q-HoE-1).

**Save version:** **no bump. SAVE_VERSION stays 6.** Add an optional `breeds?` field, following the `tracksV7` / `seenTracksExplainer` precedent (`state.ts:22,26`).
- A bump to 7 would make every M4.1 build refuse the save as "newer", so the game would be read-only and roll-back blocked (`save.ts:87-89`, `game.ts:61`).
- Older builds keep the unknown key untouched: `migrate` spreads `d.state` (`save.ts:101`), `step` and `apply` spread state (`tick.ts:50`), and `flagOffShape` strips only the track keys (`save.ts:162-166`).
- The "migration" is a lazy default plus a sanitiser on read. It isn't a `migrations[]` entry.
- Required test: a save with breeds data loaded and re-saved by the M4.1 flag-off code path round-trips byte-identical in `state.breeds`. This is BR-AC1 clause 2.

## 2. Telemetry names and fields (Q-HoE-2, §8)

- **Event names fit.** Every RC1 event type is snake_case (`goal_tap`, `offline_grant`, `save_migrated`, … via `telemetry.track`). Sim events reach telemetry automatically through `Game.emit` (`game.ts:106-115`). `breed_revealed`, `breed_slotted` and `flock_complete` are fine. New fields in snake_case match `collection/telemetry-spec.md` (e.g. `refund_cents`, `farm_level`). The legacy camelCase fields (`secondsAway`, `newLevel`, `coinsBefore`) stay as they are.
- **Don't reuse `upgrade` for the hatch (change R1).**
  - `upgrade` has a required shape `{upgrade: 'collection'|'farm'|'hens'|'eggValue', newLevel, cost, coinsBefore, track?}` (`src/sim/events.ts:9`). Its `cost` is already in cents (`actions.ts:29,36`), so adding `cost_cents` would duplicate it.
  - Upgrade-based KPIs would also count hatches: TTFU / `is_first_upgrade`, upgrades per session, and `first_upgrade` in `session_summary` (telemetry-spec T-AC5, L79).
  - Use a new **pinned** `hatch_started{breed_id, rarity, cost_cents, pity_before, free, farm_level}` instead. If HoQA insists on reuse, it must carry the full existing shape (`upgrade:"hatch"`, `newLevel: hatches`, `cost`, `coinsBefore`).
- **`flock_complete` pinned:** add it to `isPinned` (`src/telemetry/telemetry.ts:12-15`). "Once per save" doesn't need a flag, because it fires only on the reveal that completes the flock.
- **`save_migrated{reason:"breeds_sanitised"}`:** the existing shape has no `reason`. It's `{from, to, migration, refund_cents, farm_level, backup_stores}` (`game.ts:246`). Use `migration:"breeds_sanitise"`, `from:6, to:6`, or a ring event `breeds_sanitised`.
- **Dependency:** RC1 events carry `ts` + `sessionMs`, not `sid` + `fgMs` (`telemetry.ts:16`), and `session_end` has **no payload** (`game.ts:297`). The §8 `session_end` extensions and the envelope need the M5.0 telemetry subset merged first.
- `offline_grant.away_bp` is fine (it's added at `game.ts:103`). New event names still need HoQA's OK (Q-HoE-2).

## 3. Do bots, autoplay or the pacing sim read breed state? (Q-HoE-3, BR-BB5)

- **Today, no.** Nothing in the repo knows about breeds. The AC7 bots drive `step` and `apply` directly (`tests/bot.ts:3-7`, `tests/bot-m2.ts:5-13`) and pick through `candidates` (`src/ui/next-goal.ts`) + `bestPaybackAmong` (`tests/bot-m4.ts:8-23`, `best-buy.ts:151`). Every planner read goes through `incomePerSec` → `prodEggsPerSec` (`income.ts:62-64`, `tracks.ts:13`).
- **They never will if these hold (put them in the spec):**
  1. The Present term needs an explicit focus input to `step` (e.g. `step(s, dt, b, ev, focusDt = 0)`). The bots call `step(s, dt, b, ev)` with four arguments, so they get 0 Present by construction. RC1's `step` is pure and has no focus notion (`tick.ts:10`), and focusClock is M5.0 (no `focusClock` exists at 5d9efa6).
  2. `initialState` has no `breeds` key, and the bots never hatch. All breed code no-ops when the key is absent, the flag is off, or slots are empty.
  3. `breeds.rng` is a separate stream, so `s.rng` (`tick.ts:36-48`) is untouched. That's OK for the trace hashes. Nit: seed it with `mixSeed(s.rng ^ K)` rather than a raw copy, so the first rolls aren't the customer-demand sequence. It still never advances `s.rng`.
- **Enforcement (all three, in the tests PR):**
  - (a) BR-AC1, AC2 and AC24 hash identity on seeds 1–200, with the flag off and with the flag on and no hatch, in CI.
  - (b) An **import-boundary test**. The repo has no ESLint (`package.json` devDeps), so use a vitest that fails if `src/econ/**`, `src/ui/{next-goal,goal-label,pick-hysteresis}.ts` or `tests/bot*.ts` import `src/sim/breeds*` or read `.breeds`.
  - (c) A BR-AC21 property test: random loadouts give identical `options`, `bestBuy`, `optionGain`, `paybackOf` and `bestPaybackAmong` results.
- **Flag:** Economy's E-1 "hatcher" profiles necessarily read breed state. They must be **separate harness profiles, outside the AC7 hash set**, and the AC7 profiles stay hatch-free.

## 4. Where the Present lay bonus applies (Q-HoE-4, BR-R12, BR-BB2)

- **Tick only, outside `prodEggsPerSec`: agreed.** It's consistent with the code.
  - `bestBuy`, `optionGain` and `paybackOf` all score with `incomePerSec(…, {assumeWorking:true})` (`best-buy.ts:73,82,100,116-122`), and `incomePerSec` uses `prodEggsPerSec` (`income.ts:63`). The goal label's % reads the same values (`goal-label.ts:38`).
  - Putting the term next to the coop fill at `tick.ts:24` keeps ★, the hint and the hatch cost breed-neutral, as the spec intends.
- **Offline drift: none introduced.** With M4 on (`balance.json:164`), the grant **doesn't use `prodEggsPerSec`**. It uses the CSV `offline_eggs_per_sec[H]` / `offline_max_eggs_2h[H]` (`offline.ts:7-10,21`). `prodEggsPerSec` is used only in the M4-off branch (`offline.ts:22`, the line the spec cites). Offline and online rates already differ by design, so a tick-only Present bonus can't make offline drift, and that's the point of the Away family.
  - Apply Away in `m4OfflineEggs` as `floor(min(min(away,cap) × rate × (10000+awayBp)/10000, maxEggs2h) × mult)`. Fix that exact float order in BR-AC17 so goldens match to the egg.
- **Known estimator gap (accepted, document it):** with Present slotted, real in-tab income is up to ×1.15 above `incomePerSec`. `secondsToAffordSteady` and the ETA (`income.ts:95-100`), plus the "≈N s of income" label, will be conservative, by up to ~13% too long. They're never optimistic. That's acceptable, and it keeps the label and ★ consistent with each other. The alternative, folding Present into the estimator, would break BR-BB2.
- **Where `dtFocus` goes:** pass it into `step` (see 3.1). `Game.frame` passes the visible-frame dt capped at 1.0 s per frame when not hidden and no menu is open. The hidden branch (`game.ts:389-396`) and `debugAdvance` pass 0. `Game` needs a `menuOpen` setter from the UI.

## 6. Money math check (integer bp, BigInt guard)

- **Hatch cost (BR-R5/R17):** `planRefCents × 45` is integer × integer. The guard boundary checks out in Node BigInt: last safe 200,159,983,438,688, first guarded …689. BR-AC6 checks out: 277,973 × 45 = 12,508,785.
  - **Simplification:** `farmStepCents` comes from integer `farmCost` (`formulas.ts:52-55`) × 100 and is always safe (F30: 62,431,600; × 10000 = 6.2e11). With `share_bp ≤ 10000` the `min()` is therefore always ≤ a safe value. The BigInt path can only ever pick the Farm branch, so the guard can be a comparison: `planRefCents > floor(farmBranch / bc_hatch_cost_s)` → take the Farm branch. Keep BR-AC13, but expect the Farm-branch result there.
- **Deviation (R2):** `floor(farmStepCents × share_bp / 10000)` doesn't follow the house rule `floor((cents×bp + 5000)/10000)`. It's exact at 10000 bp today, but the spec should use the house form so a retune can't diverge.
- **Broody (BR-R14):** the boundary checks out: 15,011,998,757 last safe at bp 600, vs 18,014,398,509 at 500. It uses the existing M5.0 R7 guard, so there's no new path.
- **bp × bp** (`traitBp`, `broodyBp_eff`) uses floor, which is why the table shows 312 / 437 for 312.5 / 437.5. That's not money, so floor is fine, but write it as integer ops. With half-up it would be 313 / 438.
- **No breed term in `saleMultipliers`** (`payout.ts:8-10`): confirmed it's compatible. A planner-income float is rounded once with `Math.round(… × 100)`, per the I_ss rule.

## 7. Risks and required spec changes

- **R1** Use `hatch_started`, not reused `upgrade` (§2).
- **R2** Hatch-cost bp step must use the house rounding (§6).
- **R3** The offline decrement uses the clamped `awayS`, not the full span. Reveal and auto-slot are one pure function shared by `step` and `applyOffline`. The load-time reveal goes through a `pendingReveal` field (§1).
- **R4** Present needs an explicit `focusDt` argument to `step`, with a default of 0 (§3, §4). Hard dependency on M5.0 focusClock.
- **R5** Say explicitly: optional v6 field, **no SAVE_VERSION bump**, plus an M4.1 round-trip test (§1).
- **R6** Hatcher bot profiles are outside the AC7 hash set (§3). Import-boundary test plus property test in CI.
- **Risk:** in-tab ETA is conservative by up to ~13% with Present slotted. Accepted, but add a line to the UX copy notes.
- **Risk:** the `m4.flags` namespace doesn't exist in RC1. Coordinate with the M5.0 flag owner so it's created once.
- **Doc nit:** the incubator assumption PM Collection called "§13" is actually in BR-R8 / R18 / R20 and §6. §13 is the Economy list.
