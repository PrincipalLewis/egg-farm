## 3. Aria = exact amount: FAIL
**MK-24-1-A11Y (Medium):** buttonAria uses `fmtMoney`, which is exact only under $10K. From $10K up it uses fmtCount (round to nearest, 1–2 dp). Repro: `orderView({demand:10,filled:0},1,()=>999900000)` gives button "+$9.9M" and aria "+$10M". So the aria is neither exact nor ≤ the credit; it can overstate. Example: $12,345.67 reads "$12.3K". Fix: use a full exact formatter for aria (e.g. `$` + toLocaleString with 2 dp), or a spelled-out form.

## 5. Art & UX row-2 question (17 eggs $93.84, 'Sell 13 +$71.76'): CONSISTENT, not a bug
Engineering's MK-24-1 save in a real browser (Chromium 390 mobile, plus Firefox 390), chromium-e2e.log / firefox-e2e.log:
- Row 2 is demand 17, filled 4. The card reads "17/17 eggs · $93.84" (have = filled 4 + this sell 13; value = full order). The button reads "Sell 13 +$71.76", and the aria is "Sell 13 · +$71.76".
- After tapping, the telemetry `sell` event was k=13, base price 368¢, value **7176¢**. So k matches what one tap sells, and +$X matches the credit to the cent.
- Unit price: 368¢ × grader ×1.5 = 552¢ = $5.52. 93.84/17 = 5.52 and 13 × 5.52 = 71.76. Consistent.
- Caveat (Low, latent): saleValueCents rounds `k×base×mult` per call, so with a non-integer cent unit price, card/want and button/k may differ from k×(card/want) by a cent. Each preview still equals its own credit.
- Label: "17/17" for a partially filled order may read as "already full". That's a UX call for Art & UX/Product, not a money bug.
