## Findings

**F-1 (minor) — O-3: nothing fails loudly when bot-m5's own M5 mechanics and the real flagged M5 code are both active.**
- **Location:** `scripts/verify/sim.ts:120-135` (`runM5xCasual`), `tests/bot-m5.ts:33-35`, `scripts/verify/cli.ts:49-60`, `scripts/verify.ts:64,100,117`.
- **Trace:**
  - `flagsOf` now lists `m4.flags.*` (`cli.ts:52`). `withFlags` accepts `m4.flags.streak=1` (`cli.ts:59-60`), and `verify.ts:64` passes the flagged balance to `runVerify`. For `m5x-casual`, that reaches `runM5(b, …)`.
  - `bot-m5.run()` takes `bal` and spreads it (`bot-m5.ts:35`). It never reads `m4.flags` (`rg flags tests/bot-m5.ts scripts/bot-m5x.ts` finds only a comment at `bot-m5.ts:8`). It layers its own streak, golden, abilities, Broody and pause on top (`bot-m5.ts:41-75`).
  - No assertion, throw or test checks `anyM5FlagOn(b)` (`src/sim/timers.ts:20`) against this profile. `tests/bot-m5.test.ts` and `tests/verify.test.ts` never run `m5x-casual` with an M5 flag on.
- **Why it's only minor today:** only `seedEvRng` (golden/broody) and `isPaused` are wired, plus an empty effects registry. A double count is not yet possible. An override such as `m4.flags.streak=1` also forces exit 4 (`flagsDifferFromBuild`, `verify.ts:117-120`), but the message only says the flags differ from the build.
- **Where it gets worse:** when a feature PR lands and the shipped flag flips to 1, an unflagged `--profile m5x-casual` run will silently double count. It will exit 0, and the golden checks will not catch it because the bot is not on the golden path.
- **Repro (traced, not run):** `npm run verify -- --hours 1 --profile m5x-casual --flags m4.flags.golden=1 --no-shot`. There is no usage error. The run completes with the bot's golden model plus `evRngState` seeded by the real `seedEvRng`, and exits 4.
- **Suggested fix:** in `runM5xCasual` (or at the top of `bot-m5.run`), throw when `anyM5FlagOn(b)` is true, with a message like "bot-m5 models M5 itself; flags must be off". Add a test for it. Do this before the first feature PR flips a flag.

**F-2 (minor) — `src/config/m5-rules.ts:14,29`: `M5_REQUIRED_TC` is empty, so a flag turned ON with its tc keys missing validates, and the save sanitiser silently defaults them to 0.**
- **Evidence:**

  - It is already used under flags at `m5-fields.ts:33` (`egg_gap_*`), `:39` (`streak_decay_per_s`), `:48` (`ability_s`), `:59` (`frenzy_s`) and `:68` (`ability_cd_s`).
  - The header says "the feature PR that reads a key adds it", but F2 already reads these keys. `validateM5` with `flags.golden=1` and `egg_gap_max_s` removed does not throw (`has()` is false, so every rule is skipped and `M5_REQUIRED_TC` is `{}`).
  - The `no tc.x ?? n` grep test at `tests/v5-f3-config.test.ts:113` does not catch this form (`tc(b,k)` with `?? 0`).
  - The required-key loop at `m5-rules.ts:29` is dead code with no test.
- **Impact:** nothing is wrong at ship, since all five keys exist in `balance.json:385-408`. This only matters for a future CSV or hand edit that drops a column with the flag on.
- **Repro:** `validateBalance(withTc without egg_gap_max_s, flags.golden = 1)` passes. `sanitizeM5` then sets `nextSpawnRemainingS = 0`.
- **Suggested fix:** populate `M5_REQUIRED_TC` for the keys F2 already reads (golden, streak, abilities) and add one test.
