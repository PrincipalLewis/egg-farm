## Review of 9601303 (QA TUT-1)

### What it does and why it is right

- **Root cause.** Docked (landscape ≥960px), `openPanel` returns early and keeps `open = null` (`app.ts:157`), while the Market panel is always visible and `render` already feeds `orderList` when `open==='market' || docked.matches` (`app.ts:506`). The tutorial target and caption for step 1 only tested `open==='market'`. Docked, they fell through to "tap the customer chip". That tap calls `openPanel('market')`, which does nothing there, so the tutorial never reached Sell and a new desktop player was stuck until the 60s gate timeout.
- **Target and caption.** The target (`app.ts:609`) and caption (`app.ts:~611`, `open === 'market' || docked.matches ? 'Tap <b>Sell</b>…'`) now use the same predicate, so the text and ring agree. Precedence is fine: `a || b ? x : y` parses as `(a||b) ? x : y`.
- **Behaviour on rotation or resize.**
  - docked → undocked: `docked.matches` is false and `open` is null, so the target falls back to the chip. Tapping it opens the panel, and the next frame targets the Sell button.
  - undocked → docked with the sheet open: still `open==='market'`, so the target stays on the Sell button.
- **Event flow.** Step advance is driven by the `sell` event with `by === 'player'` (`onboarding.ts:36`), not by which element was tapped. The Sell button's `click` goes through the existing `mRows` handler. The target is the first `button[data-id]`, which is also the first FIFO order.
- **Chip click handler.** `if (ok) openPanel('market')` became `if (!ok) return; openPanel('market'); …`, which is equivalent for the original behaviour. `chips` is declared later (`app.ts:274`) than the handler (line ~200), but it is only read inside the click callback after mount, so there is no TDZ risk. `chips` is keyed by customer id and `.order` rows use `data-row="${id}"`, so the lookup is consistent. `mRows.querySelector('.order:not([hidden])')` is a sensible fallback.
- **Tests.**
  - The unit regexes match the committed source: `if (st === 1) return open === 'market' || docked.matches ? mRows.querySelector('button[data-id]')` and `if (docked.matches && c) {…\.order[data-row=…` on one line, plus `retrigger(row, 'goal-hl')`.
  - The `rc0 tut1docked` section is well designed. It uses a new player and 3 docked viewports. It locates the ring and hit-tests `elementFromPoint` through it. It requires the hit element to be a `#mRows` button with `data-id`. It then clicks at that point and asserts coins increased, the saved `onbStep` in `eggfarm.ui` advanced and no `pageerror`. This tests the actual failure mode (a "target" that doesn't sell), not just the selector. `open({w,h})` matches the helper signature (`rc0-browser.mjs:18`).

### Findings

#### Minor

**G1. The docked "card tap highlights its order row" feedback is wiped by the next list render** (`src/ui/app.ts:203-204` with `src/ui/order-list.ts:28`)
- The new code adds `goal-hl` to the `.order` row with `retrigger(row, 'goal-hl')` and removes it after 1200ms.
- `OrderList.fill` runs for every existing node on every `apply`. Its first line is `if (el.className.replace(/ (enter|leaving)/g, '') !== cls) el.className = cls + …`, where `cls` is `order ${v.state}`. A row carrying `goal-hl` therefore never equals `cls`, and `fill` resets `className`, removing `goal-hl`.
- `apply` runs from `orderList.update(...)` in `render` (`app.ts:511`), which also drives the avatar rings (line 512), so it runs about once per frame. So the highlight most likely shows for at most a frame instead of 1.2s. The upgrades-row highlight avoids this with the `hlSel`/`hlUntil` re-apply (`app.ts:415`, `520-524`) because that panel is rebuilt with `innerHTML`. The orders list is not.
- Impact is cosmetic. It is only the tap-to-find feedback, and `scrollIntoView` still works. The tutorial fix does not depend on it, and the TUT-1 unit test (source regex) and the rc0 section (which never taps a chip) do not exercise it, so nothing would catch this.
- Suggested fix: preserve extra classes in `fill`, for example compare `classList.contains('order')`/state class rather than the whole `className`, or keep `goal-hl` in the preserved-token regex `/ (enter|leaving|goal-hl)/` in both places. Alternatively apply the highlight through the same re-apply pattern as `hlSel`.
- Confidence: high on the code path, not confirmed by running it. If `render` is throttled harder than I read, the flash would be longer but still shorter than 1.2s.

#### Nit

**G2. "+N" chip and repeated taps** (`app.ts:203-204`)
- The "+N" overflow chip also matches `.chip:not(.empty):not(.served)`. It is not in `chips`, so `id` is undefined and the fallback highlights the first visible row. That is acceptable, but it means "+N" tap shows a highlight that implies a specific customer.
- Two taps within 1.2s let the first `setTimeout` clear the second highlight early.
- Neither matters unless G1 is fixed.

**G3. The two TUT-1 unit tests are source-text regexes**
- They pin exact source spelling, such as `[^\n]*\.order\[data-row=` on the same line, and will break on any reformat while not proving behaviour. Behaviour is covered only by the rc0 section. This matches the file's existing style, so it is only a note. The rc0 `tut1docked` section remains the real guard, so please make sure it runs in the QA pass.
