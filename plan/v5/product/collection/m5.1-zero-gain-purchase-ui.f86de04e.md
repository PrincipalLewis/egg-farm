## 1. Change summary
With the flag on, an upgrade row whose next step adds **no income and no capacity** at the moment of purchase is shown as zero-gain, per the UI doc of record:
- a **`No gain now` chip** after the effect text;
- **only the effect line muted, including its `→` arrow**;
- **no affordable glow** on Buy;
- the accessibility fact in Buy's **`aria-describedby`** (the accessible name stays the cost).

There is **no `+0`** anywhere and **no row-level dim** (Art Q-Art-1/2, 03:10 Q-ZG-A2).

The row also never receives the ★ and never lights the Upgrades nav dot (D-HOP-09; Art 03:10 Q-ZG-A1). Buy still works. Which rows are zero-gain comes from the game's own gain function, read-only.

## 2. Goals
- **G1** A player can see, before paying, that a purchase changes nothing for income or capacity right now (D-HOP-08).
- **G2** A zero-gain row never carries ★, the hint, the highlight or the nav dot, on either picker. Not muted ≠ recommended (PMFU Q-ZG-P1).
- **G3** The player keeps the choice. Nothing is hidden or disabled, and no economy value changes.
- **G4** Measurable with flag-on telemetry (§10).
- **Non-goals:** K-F1 (owned by PMFU, M5.2); the CSV choice for rows 27–29; BBv2 logic in `econ/best-buy.ts`; the pacing bot; the rc1 worker chip; Art minor m10 (disabled Buy contrast, Art 03:10 Q-ZG-A4).

## 5. Behaviour
### 5.1 How the game computes a purchase's effect
- **Income model:** `incomePerSec(s) = min(prodEggsPerSec, demandPerSec, collectPerSec) × priceDollars − wagesPerSec` (`incomePerSec` in `econ/income.ts`, cited by name; HoE 03:42). This is a steady state, a plain JS number in **$/s, not integer cents**. The probe at `30b29d3` found non-integer-cent values such as 9.742120343839542.
- **Single-step gain:** `optionGain(s, b, key).gain = incomePerSec(after) − incomePerSec(s)`, `assumeWorking: true` (`econ/best-buy.ts:113-117`). The offered keys come from `options()` (`:44-67`).

### 5.2 Gain, defined mechanically (D-HOP-09 Q-ZG-H1; HoE 02:55, 03:02)
- **Δincome(key)** = `incomePerSec(after) − incomePerSec(s)` with `assumeWorking: true`, breed-neutral. This is the same function and the same inputs as `optionGain`, ★, `bestRoiDelta`, the stopgap and BBv2 §5(g).
- **Δcapacity(key)** = `trackCoopCapacity(F′, H′) − trackCoopCapacity(F, H)` (`formulas.ts:130`), using the option's `after` levels and the same balance data. **No second capacity formula** (HoE 02:55). It is 0 for COLL and VALUE. For HENS it is > 0 only on steps to H = 10/20/30 (probe: F17 H19→20 gives +225 = ⌊900 × 1.5⌋ − ⌊900 × 1.25⌋, col 7 level 17).
- **Pure and read-only (HoE 02:55):** the check never mutates `s`, dispatches, or touches rng or time. It is one UI helper, `isZeroGain(s, b, key)`, which delegates to a pure exported **`zeroGainVerdict(incBefore, incAfter, dCap)`** (HoQA F5). `econ/best-buy.ts` is not edited (HoE 02:58).
- **Comparator (HoE 03:19, correcting 03:02; Q-ZG-E4 CLOSED):**
  - `zeroGainVerdict = (incAfter <= incBefore) && (dCap <= 0)`. It compares **the unrounded $/s** from the same single-step income function on the same inputs: plain JS numbers, no rounding to cents, **no ε**. Any gain > 0 counts (D-HOP-09).
  - The build adds a **dev assert** on both compared values: `Number.isFinite(x) && Math.abs(x) <= 2**53`. It is not a safe-integer check.
  - `NaN` fails the dev assert (throws). Without asserts, JS gives `NaN <= x === false`, so the verdict is false (not ZG).
  - Any other number type is a separate future decision, out of scope (HoE 03:02/03:19).
- **Exempt keys:** FARM and W1–W4 are never ZG. **Closed by D-HOP-37** (BBv2 v0.3 `f128f1e6` pinned, `product/decisions.md` L942; PMFU Q-ZG-P1; HoP L1159).
- **ZG row** = a non-exempt offered key (COLL, HENS, VALUE) with `zeroGainVerdict` true (D-HOP-09 Q-ZG-H1: "any gain > 0 is not zero-gain"). No threshold.
- **Partial gain** is never ZG: (a) any Δincome > 0; (b) Δincome ≤ 0 with Δcapacity > 0 (HENS milestone steps). (b) shows only the existing "bigger coop" hint (Art Q-Art-5).

### 5.2a Evaluation window and persistence (v0.3.6; D-HOP-2026-10-29-08 (8); explicit from approved text, no rule change)
- **The evaluation has no time window.** The verdict is instantaneous: a pure function of (F, C, H, V, hired workers, graderTier, b) for the current state (§5.3 Determinism; §10 "ZG is a pure function of levels, workers and balance"). It compares steady-state $/s before and after one step (`incomePerSec`, §5.2). There is no averaging period, no look-ahead or payback horizon, and no dependence on coins, moods, energy, time or rng (ZG-AC7).
- **When it is re-evaluated:** on every render. A level, worker or Grader change gets a new verdict on the next render (E13). A load or offline return is classified on the first render (E15).
- **How long the treatment persists:** exactly as long as the verdict is true. There is no hold, no hysteresis and no minimum display time. A ★ row that turns ZG leaves the rows at once, with no 2 s hold (E17). There is no save field (E15), so nothing carries over a reload. The confirm strip (UI doc v1.4) is UI state, not a verdict. If the row stops being ZG, the next render drops the `.zg` row state.

### 5.3 Caps, gates, multipliers not yet active
- **Not offered by `options()`:** no ZG, no picker change. This covers locked rows (`Needs Farm L6` visible text, per Art 03:10 correction), MAX, `Max for this farm`, workers below unlock, and Farm or Collection at `maxLevel`.
- **Coop full / lay caps:** not in the steady model. Taps to empty the coop are not gain. Example: F27, H 20–29 gives ⌊1,400 × 1.5⌋ = 2,100, which takes 15 taps at C27 (140) and 15 at C28 (145). My choice.
- **Inactive multipliers:**
  - Bundle value is not gain (single-step, BBv2 §3).
  - Egg grade 3 before F15: VALUE Δincome is still > 0.
  - Asleep or unpaid workers are scored as Working.
  - Breeds are invisible to planners (BR-BB2, BR-AC21).
  - Frenzy, streak and tap coins are not in `incomePerSec`.
- **Determinism:** ZG is a function of (F, C, H, V, hired workers, graderTier, b) only.

### 5.4 Flag and tunable (D-HOP-09 Q-ZG-H2; HoE 02:55, 02:58)
- **`m5.flags.zeroGainUi`:** balance.json, default 0, synced with `m5.flags` (HoE 02:55). It **requires only `m4.enabled`**, independent of `m5.flags.bestBuyV2` (HoE 02:58). It is **read once at boot**; a change needs a reload. With `m4.enabled` 0 it is ignored.
- **`m5.zeroGain.confirm`:** a balance.json **tunable**, default **false**, **off in M5.1** (HoE 02:55; Art Q-Art-4). No player-facing toggle.
- **Dependencies:** none on BBv2 or D-CEO-15/16 (D-HOP-09).

### 5.5 Display-only difference vs ★ / BB-10 (PMFU Q-ZG-P1; D-HOP-37)
BBv2 / BB-10 stay income-only. A HENS milestone step with Δincome ≤ 0 and Δcapacity > 0 is not muted and not ★-meaningful. HoP accepted this (L1159). **Closed.**

### 5.6 ★ rule: one source, filtered before the pick (D-HOP-09 Q-ZG-H2; HoE 02:58)
- `bestBuyMark` (`goal-label.ts:96`) stays the one source. It is fed by the UI `DualPicker` (`app.ts:418`), whose two `PickHysteresis` instances hold the hysteresis. The strip and the row chip share it.
- **Flag on:** `app.ts` builds `new DualPicker(filtered(defaultScorer), filtered(allScorer))`. The constructor already takes `(hl, all, sig)`. `filtered` drops rows where `isZeroGain` is true **before the pick**.
  - The ★ therefore goes to the best non-ZG row, and is null only when no non-ZG row is offered.
  - `PickHysteresis.evaluate` returns null on empty rows, and `keepable` needs the row in `rows`, so E17 holds (verified by HoQA).
  - `pick-hysteresis.ts` exports are unchanged, and the hysteresis state stays in the UI.
- **Fallback to unaffordable** (`bestOf(aff.length ? aff : rows)`): if every affordable offered row is ZG and at least one unaffordable non-ZG row is offered, the hint is that unaffordable row and `bestBuyMark` is null. The strip names it **without ★** in its existing unaffordable status (E18, ZG-AC17b; HoQA F8).
- **No picker at all** (every offered row ZG): the strip takes its existing no-pick path (`selectGoal(…, undefined, null)`, `app.ts:428`), or BR-BB4 with breeds on (see the ZG-AC17 breeds-on variant). No new pointer (Art Q-Art-7).
- **Not touched:** `econ/best-buy.ts`, `tests/bot-m4.ts`, AC7 (HoE 02:58).
- **Baseline and stopgap (HoQA F1, T3; HoE 03:19):**
  - The test baseline is **M5.0-merged main, SHA pinned at kickoff (HoE, `engineering/decisions.md`)**, with `zeroGainUi` absent. Tests pin that SHA.
  - Current main `d1fb206b` has no stopgap and no M5 code; `30b29d3` has the single-argument `bestBuyMark`. Neither is the M5.1 base.
  - The M5.1 base **includes the M5.0 bb-stopgap** (`bestBuyMark(pick, s, b)`, SG-1/3/8; HoE 03:19). So with the flag on, the following are **the expected case**:
    - (a) SG-1 suppression still applies to a picked HENS milestone row with gain ≤ 0, so ZG-AC3 reads "★ only if picked **and** meaningful";
    - (b) SG-3 and the SG-8 tests are pinned to `zeroGainUi` off;
    - (c) SG-8 is expected to fire **0** times with the flag on, since no ZG row is ever picked.
- **BBv2 runs (HoQA F2/F3), conditional on BBv2 landing:**
  - `m5.flags.bestBuyV2` exists in no build (HoQA: not in `src/` or `data/` at `30b29d3` or on any local ref; my `rg -i bestBuyV2 src data scripts` at `30b29d3` also finds nothing).
